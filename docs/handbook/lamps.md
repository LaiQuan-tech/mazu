  **燈種可以設「請信眾選擇」一格**（2026-11-17 廟方：「專屬神明燈，還需要有神明燈的表單，須在後台可設定」）。後台點燈管理 → 編輯燈種 → 欄位名稱＋選項（一行一個，可「從祀奉神尊帶入」）；前台選到那個燈種才出現、必選，揪團表單也有。**設定存 `site_settings.lamp_choices`（JSON）、信眾選的值寫進該筆 `notes` 開頭「【指定神明】觀世音菩薩」，兩者都不加欄位**——好幾支 migration 到現在沒跑，新欄位會被 `insertOptional` 安靜丟掉，廟方就看不到信眾選了誰。後台列表把它併進燈種標籤、匯出多一欄「指定項目」（`readChoiceTag()`）。要改成正式欄位時用同一支函式回填舊資料。**新增的燈種要先存檔再編輯才設得了**（沒有 id）。
  **每個選項可以有名額**（同日廟方：「還要有數量限制」，問過是「每尊神明各自有名額、每年九月重算」）。後台選項框**行尾的數字就是名額**（「天上聖母 30」，沒寫＝不限；`parseChoiceLines`），存在同一份 JSON 的 `quotas`。前台每個選項標「剩 N 盞／已額滿」並停用額滿的，**要扣掉同一張表（與揪團表）裡其他人已選的**；送出前**重抓一次計數再比**（`quotaShortfall`），揪團在主揪送出那一刻也比。計數走 `get_lamp_choice_counts` RPC（`supabase/migrations/lamp_choice_counts.sql`，**使用者尚未執行**）——anon 讀不到 lamp_registrations，這支只回「選項→盞數」。**讀不到計數時一律放行不擋**，後台編輯視窗會顯示黃色提示要跑那支 SQL。季的起點 `lampSeasonStart()` ＝九月一日台北時間，與干支換年同一條界線。已知限制：兩個人在同一秒搶最後一盞擋不住（只有前端檢查），廟方從後台看得到、自己處理。

- **導覽列上「點燈服務」與「祈福活動」依農曆月份自動換位**（2026-10-01 廟方要求）：點燈是年度服務，信眾集中在農曆年底年初來點（安太歲、光明燈都是為新的一年點的），年中擺在前段只是佔位置。**農曆十一月、臘月、正月**點燈服務排在導覽列，其餘月份退到「更多」、由祈福活動遞補。
  **是互換不是各加一個**：桌機頂層那一列沒有空間（1024px 時用掉 949px、可用 945px），多一項就擠出去；兩個標籤都四個字，換了寬度不變。判斷在 `isLampSeason()`，農曆月份由 `currentLunarMonth()`（`services/lunarCalendar.ts`）取，**閏月算同一個月**（lunar-javascript 用負數表示閏月，取絕對值）。
  **每次載入頁面算一次，不做即時更新**：月份一天只變一次，為了跨月那一刻掛計時器等於多一條會忘記清掉的訂閱。實測切換日：2026-12-09 開始排前面、2027-03-08 退回更多、2027-11-28 再排前面。

  改名動到：導覽列、`document.title`、`prerender.js` 的 ROUTES（title/h1/desc）、`index.html` 的 title／og／twitter／JSON-LD Offer／noscript、公佈欄衍生卡的標題。h1 從「祈福點燈，光明護佑」改成「年度點燈，光明護佑」——「年度」正是它與單場次點燈最大的差別。

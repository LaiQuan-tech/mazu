- **報名成功會寄一封信到廟方信箱**（2026-10-11：「工作人員還不習慣開啟後台，可以有人報名後，也同步 email 嗎？」）。`services/notifyRegistration.ts`（前端）→ `api/notify-registration.ts`（後端寄信）。六種報名都接了：問事／點燈／祈福／法會／志工／捐獻。
  **前端只送 `{ table, id }`，信的內容由後端自己回資料庫撈。** 讓前端送內容等於把那支端點變成「誰都能叫它寄任意文字」的垃圾信發射器。撈不到就不寄，所以寄出去的一定是真的存在的報名。撈取用 `SUPABASE_SERVICE_ROLE_KEY`（報名表的 RLS 不讓 anon 讀回自己剛寫的那筆）。
  **三條不可違反的規則**：不 `await`（信眾等的是「報名成功」畫面，不是等信寄完）、不丟例外（通知失敗不可以讓報名看起來失敗）、沒設定環境變數時回 204 安靜跳過。
  **防重送**：建立超過 10 分鐘的紀錄不再通知。就算有人猜到某筆的 UUID，也只能在那十分鐘內讓廟方收到重複通知。
  **環境變數都不加 `VITE_` 前綴**（`RESEND_API_KEY`／`NOTIFY_TO`／`NOTIFY_FROM`／`SUPABASE_SERVICE_ROLE_KEY`）——加了會被 Vite 內嵌進前端 JS，等於公開金鑰（同 `VERCEL_DEPLOY_HOOK_URL` 的理由）。
  **本機看不到效果**：`vite dev` 不跑 `api/`，那支呼叫一定 404，是正常的。
  **一筆訂單只寄一封，不是一個人一封**（2026-10-12 廟方：「揪團是像同一筆訂單。只要最後通知一次即可。」）。
  同一個理由也適用一般表單的多人報名——一次替全家點燈是一筆訂單，一人一封會讓五個人變成五封信，
  真正的重點反而被自己洗掉。
  作法：`submitBooking`／`submitLampRegistration`／`createBlessingRegistration`／`submitDonation`
  **回傳自己的 id**，並接受 `{ notify: false }`；多人路徑先不寄，收齊 id 之後
  `notifyRegistration(table, ids)` 整批送一次。後端的 `id` 收得下陣列（上限 `MAX_IDS = 50`，
  防灌不是業務限制），一個人照原樣、多人合成一張名單，主旨是「王小明 等 5 人」。
  **七條多人路徑都要接**：一般表單的點燈／問事／捐獻／祈福，揪團的點燈／祈福／問事。
  法會（一列帶 `entries` jsonb）與志工本來就是單筆，不受影響；神尊修復那支單筆捐款也維持原樣。
  **部分成功也要通知**：那幾筆已經在資料庫裡了，廟方該知道；剩下的重送時再寄一封。
  **整批裡混到過期的 id 只丟掉那幾筆**，不要讓整團都收不到通知。
  `submitSequentially()`（App.tsx）因此改成回傳成功那幾筆的 id 而不是筆數，筆數用 `.length` 取。
  實測：三筆問事一次送出→收到一封「預約問事　測試－王大明 等 3 人」，`delivered`。
  **寄信網域要在 Resend 後台按「Verify DNS Records」才會生效**（2026-10-11 卡在這）：
  DNS 三筆全部填對、值逐字元一致，Resend 仍然退件 `The heshengtan.tw domain is not verified`——
  因為它的 `status` 是 `not_started`，**Resend 不會自己去檢查**，要人按那顆鈕。
  查法：`curl 'https://heshengtan.tw/api/notify-registration?domains=1'`，會列出每個網域的狀態
  與 Resend 自己要求的每一筆記錄（含完整的 DKIM 值）。沒有這支就只能在
  「沒按驗證」與「記錄填錯」之間猜，而兩者的症狀都是「信沒來」。
  **不要拿同帳號其他已驗證的網域反推該填什麼**：heshengtan.tw 用的是較新的 CNAME 式
  （`send`→`send.forge.rmta.net`、`rsend`→`rsend-apne1.forge.rmta.net`），而 laiquan.co／pikt.ag
  是舊的 SES 式（`send` 的 MX→`feedback-smtp.ap-northeast-1.amazonses.com`＋SPF TXT）。
  我照舊的那套反推，結論是「`send` 被設成 CNAME 是錯的」——完全相反，那筆正是對的。
  要知道該填什麼只有一個可靠來源：問 Resend 這個網域自己的 `records`。
  **寄送失敗會把 Resend 說的原因回傳**（信箱遮成 `***@***`，那支是公開端點）。
  原本只 `console.error` 進 Vercel 的函式 log，而廟方不會去翻那裡。
  **「Resend 回 200」不等於「Gmail 收到」**：退信與進垃圾桶也都是 200。寄送成功會回傳
  Resend 的信件 id，拿去 `?email=<id>` 才看得到 `last_event`（delivered／bounced／complained）。
  這個功能存在的理由就是「工作人員不會去看後台」，信靜靜地沒送達等於整個功能死掉而沒人知道。
  **2026-10-11 實測通過**：問事報名→信件 `delivered`。其餘五種是同一條路徑，
  差別只在 `TABLES` 的那一行；六張表都實測過「anon 帶著自己產的 id 寫得進去」
  （只送 id 探測，五張表都回 `23502 null value in column "name"` 而不是 `42501`，
  證明權限沒擋、而且不會真的建立資料——這招用來驗權限不留垃圾資料）。
  **收件信箱 2026-11-18 再驗一次：正確**。廟方指定一個管理用 Gmail，`NOTIFY_TO` 就是它——在官網送一筆「測試－通知信」的點燈登記，`?email=<id>` 回 `delivered`，廟方確認那個信箱收到了（測試資料已用 SQL 刪除）。
  **信箱地址刻意不寫在這裡**：這個 repo 在 GitHub 是公開的。地址在 Vercel 的 `NOTIFY_TO` 與本機的 Claude 記憶，**要確認就問廟方或看 Vercel，不要從 repo 找**。端點回應會把信箱遮成 `***@***`，`?domains=1` 只說得出 `NOTIFY_TO: true`（有設），說不出設成哪一個——**要驗「寄到對的人」只能真的送一筆、請廟方看信箱**。

- **信眾也會收到信：確認信與感謝信（`api/notify-confirm.ts`，2026-10-13）**。廟方：「報名經後台管理人員確認後，應該要發一個報名完成的確認信」「捐獻，直接寄感謝信」。
  **與 notify-registration 是兩件事**：那支寄給廟方（固定一個信箱），這支寄給信眾（資料庫裡那筆填的信箱）。差別造成完全不同的授權設計——
  **公開就等於「猜中任何一筆報名的 UUID 就能對那個人寄信」**，是一台針對特定人的騷擾工具。
  所以問事／點燈／祈福／法會這四種**要管理員身分**：把登入者的 Supabase token 丟去讀 `admin_profiles`，非管理員必然拿到空陣列 → 403（同 `api/republish.ts`）。
  **捐獻是唯一的例外（`open: true`）**：它沒有「已確認」這個狀態（後台那一頁只是紀錄清單），而捐款人要的本來也不是「我們確認了」是一句謝謝，所以由前台在**送出成功當下**呼叫——送出的人就是捐款人本人，他沒有也不該有管理員 token。換來的防線是 notify-registration 那一套：**只寄「建立未滿 10 分鐘」的那幾筆**，再加 `confirm_sent_at` 蓋章。管理員那條路刻意**不設**時間窗（確認本來就是幾天後的事，身分驗證才是那邊的防線）。
  **`confirm_sent_at` 不是可有可無的**（`registration_email.sql`）：後台的狀態是一顆下拉選單，會被改來改去（按錯、改回、再改過來），沒有這一欄每改一次就寄一封，信眾收到一疊一樣的信。寄之前先看、寄成功才蓋章；**寄失敗刻意不蓋**，廟方再按一次就重試（蓋了的話那個人永遠收不到而且沒人知道）。
  **一筆訂單只寄一封**（同廟方 2026-10-12 對通知信的要求）：後台一列一顆下拉，廟方會連著點五次。`services/notifyConfirm.ts` 把連續的確認**攢 6 秒**（每次有新 id 就重新計時，因為廟方是一列一列慢慢點的，固定視窗會在他點到第三列時就先送出去）再一次送出，端點依**收件信箱**分組，同一個人只寄一封、裡面列出那幾筆。
  **離開頁面一定要補送**：攢在記憶體裡的東西分頁一關就沒了，而廟方很可能點完最後一列就關掉後台。`pagehide`／`visibilitychange` 時立刻 flush，fetch 帶 `keepalive: true`。**不能用 `navigator.sendBeacon`**（設不了 Authorization 標頭）。**token 要在排入佇列時就先拿好**：flush 最重要的那條路徑是 `pagehide`，那一刻 `await getSession()` 還沒回來頁面就被拆掉了，請求根本沒送出。
  **四個表單各加一格「電子信箱（選填）」**（`contactEmail`，問事／點燈／祈福／捐獻）。**對所有人顯示不是只給訪客**：`member_profiles` 根本沒有信箱欄位，而 LINE 登入的會員連 auth 帳號都沒有信箱（LINE 不給）——只給訪客看的話，最可能需要通知的那群人反而填不到。用信箱註冊的會員會**自動帶入帳號那個信箱**（看 `member`／Supabase 的 User，不是 `memberProfile`，所以不能併進那支自動帶入的 effect）；帶進來信眾才看得見、才改得掉，悄悄寄到他兩年前註冊的信箱而畫面一片空白是在替他決定。
  **沒填的人拿電話回頭對 `member_profiles`**（廟方選的方案）。逐字比對：會員自己報名時填進去的就是那一欄的值，所以對得上；訪客手打格式不同就對不上，那也只是回到「不寄」。這沿用了全站既有的「電話當鍵」弱點（見 `my_phone()`），**沒有擴大暴露面**——那個會員本來就能在會員中心看到以他電話報名的紀錄——但要知道這件事。
  **稱呼不可以一律用第一筆的姓名**：會員替父母點燈時那幾筆的姓名是父母的、信卻是寄給會員的，開頭會變成「王媽媽 您好」寄到兒子的信箱。取標記「本人」的那一筆（四個表單第一張卡預設就是本人）；沒有本人、姓名又不只一個時就不稱名，讓名單自己說話。
  **`in.(…)` 裡的逗號是 PostgREST 的分隔符**：整串丟進 `encodeURIComponent` 會把它變成 `%2C`，於是「兩個電話」變成「一個含逗號的怪電話」、一筆都對不到——而症狀只是「信沒寄」，從外面看不出是這裡。要**逐個值編碼再用逗號串**（值本身也要編，`+` 不編會被解成空白）。
  **後台看得出「這個人到底收到通知了沒」**：`MemberInfoModal` 與法會列表各顯示一行，三種狀態分開講（已寄出／會寄到哪／未留信箱）。少了這一行，「沒留信箱所以沒寄」與「寄了」在畫面上一模一樣，工作人員會以為信眾都知道了——而這封信存在的理由就是讓信眾知道。
  **`vite dev` 不跑 `api/`，這支在本機一定 404。** 驗的方法是 `esbuild` 把它打包成 `.mjs`、用 node 跑並 stub `globalThis.fetch` 假扮 Supabase 與 Resend；授權、時間窗、分組、去重、退件、migration 沒跑的 11 種情況都是這樣驗的（這支的分支多到不可能靠部署後手測）。
  **四種觸發**：點燈／祈福是 `已收款`（`LampRegistrationStatus`／`BlessingStatus`）、法會是 `paid`，三者都是後台按「標記已收款」那一刻；問事是 `已確認`（`BookingStatus`），它**現場收費**所以沒有收款這一步。**只有「確認／收到了」那個方向要寄**（理由見上面那條）。
  **信的內容跟著分兩種**：點燈／祈福／法會寫「款項已收到」並列出金額，多筆再加一行合計（**合計一律由明細加總、不信任任何既有的總額欄位**，同財務憑證那條原則；少算一筆的合計比沒有合計糟，信眾會拿它去對自己匯的金額）；祈福的金額是方案費＋加購，**與應收管理同一套算法**，兩邊對不起來就沒人信。問事那封反而要寫明「現場繳費，不需事先匯款」——其餘幾種都要先匯款，收到一封「已確認」很容易以為自己漏了匯款那一步。
  後台那一行的文案也分三種（`RegViewItem.mailKind`）：`confirm` 改為已確認時寄、`paid` 按標記已收款時寄、`thanks` 送出當下就寄。三種講一樣的話，工作人員就不知道自己該按哪一顆。

- **`api/` 的函式要 import 共用模組時，兩件事都會害你線上 500**（2026-10-16 各踩一次，連原本正常的端點一起掛掉）：
  (1) **共用模組不能放在 `api/` 底下**。`_` 開頭不當成路由那個慣例是 Next.js 的；這種「裸 `api/` 目錄」的專案，Vercel 會把 `api/` 底下**每一個檔**當成函式入口，而共用模組沒有 default export。放 repo 根目錄的 `lib/`。
  (2) **相對 import 一定要寫 `.js` 副檔名**。`package.json` 是 `type: module`，Vercel 把函式當 ESM 跑，而 ESM 在執行期要求帶副檔名，少了就是 `ERR_MODULE_NOT_FOUND` → `FUNCTION_INVOCATION_FAILED`。TS 這邊寫 `.js` 會解析到 `.ts`（`moduleResolution: bundler`）。
  **本機 `tsc` 與 `esbuild` 兩關都不會抱怨，只有部署上去才會炸**——所以動過 `api/` 之後一定要 `curl` 線上端點，不能只看建置有沒有過。
  **診斷的線索**：當時能動的 `keepalive`／`republish`／`notify-registration` **都沒有任何 import**，掛掉的四支都有。差異這麼乾淨的時候就照著差異走，不要先猜。

- **六種通知信眾的功能共用一支 `lib/notify-deliver.ts`**（2026-10-16 廟方一次要齊）。每一個都要做同樣三件事：拿電話對會員帳號找信箱與 LINE、依收件人分組、LINE 優先 email 墊底——複製六份就是祈福金額那種錯的翻版。
  | 功能 | 觸發 | 蓋章欄位 | 授權 |
  |---|---|---|---|
  | 確認信／感謝信 | 後台標記已收款（捐獻是送出當下） | `confirm_sent_at` | 管理員（捐獻公開＋10 分鐘窗） |
  | 匯款資訊 | 點燈／祈福**送出當下** | `payinfo_sent_at` | 公開＋10 分鐘窗 |
  | 代為報名（只推 LINE） | 後台代報送出當下 | 無（Retry-Key） | 管理員 |
  | 未匯款提醒 | 排程（送出滿 3 天、只回看 30 天） | `payment_reminded_at` | CRON_SECRET／管理員 |
  | 問事前一天提醒 | 排程（明天的場次） | `reminder_sent_at` | 同上 |
  | 點燈到期續點 | 排程（30 天內到期、只提醒已收款） | `renew_notified_at` | 同上 |
  | 年度捐獻明細 | 後台按鈕（先預覽再寄） | `statement_sent_at` | 管理員 |
  | 公佈欄群發 LINE | 後台按鈕 | `broadcast_at` | 管理員 |
  **三種提醒目前是「手動寄」，沒有排程**（廟方 2026-10-16：「手動提醒通知好了，不要自動」）：`vercel.json` 的 crons 刻意只剩 `keepalive`。要改回自動，把 `/api/cron-reminders` 那筆加回去即可（UTC 01:00 ＝台北 9 點），程式不必動——`CRON_SECRET` 那條授權路徑留著就是為了這個。
  **未匯款刻意沒有「只回看 N 天」的上限**（廟方 2026-10-16 決定）。原本有 30 天，防的是「第一次上線就對著整段歷史發一輪信」——但改成手動之後那個風險本來就不在了（廟方按之前看得到完整名單），而上限換來的是更糟的問題：**久久沒按的話，超過 30 天的人會從名單上靜靜地消失、從來沒被提醒過，而且沒有任何地方看得出來**。
  現在只剩「送出滿 3 天」這個下限，欠款的人會一直留在名單上直到被提醒或付款。代價是名單可能很長，所以明細**由舊到新排**——最可能該放棄的那幾筆排在最前面，廟方一眼看得到「這筆 700 天前的還要提醒嗎」。單次寄送仍有 `RULES.每次上限`（60 位）擋著。
  **寄送提醒的按鈕在後台「總覽」→「今天要做的事」的「可提醒信眾 N 位」那一格裡**（2026-11-18 搬進去，點開才看得到明細與「寄送提醒通知」；**全後台只有這一處能寄**，0 位時那一格不出現）。原本是總覽上獨立一組（2026-10-16 補）：平常排程自己跑，這組按鈕是給「第一次啟用前看筆數」與「排程沒跑時手動補跑」用的。**做成按鈕而不是叫人用終端機**——原本要先保管一串 CRON_SECRET、在終端機貼、貼了還看不見（`read -s` 不顯示輸入），廟方實際卡住兩次。按鈕用的是登入中的管理員身分，沒有秘密要保管。
  **排程類的時間窗是必要的不是保守**：沒有上下限的話，這支一上線就會對著資料庫裡所有歷史紀錄發一輪信，收不回來。`?dry=1` 可以只預覽不寄，**第一次跑之前一定要先 dry**。
  **`CRON_SECRET` 沒設的話排程不會自動執行**（只剩管理員能手動觸發）。這是刻意的——寧可功能先不自動跑，也不要留一個誰都能觸發的發信端點；401 的回應會把這件事講明白。
  **群發與其他通知不是同一個量級**：它送到每一位好友、收不回來、每位都算訊息配額。所以只有管理員、一則只發一次（發過的按鈕變灰字「已群發」）、還沒到 `publish_at` 的不給發，確認視窗要寫明「所有好友」「無法收回」「計入配額」。**刻意不做自動同步**——官方帳號後台本來就能群發、編輯器也比較好用，這支省的只是「貼兩次」；自動發等於每改一次錯字就打擾所有好友一次。

- **通知信眾有兩個管道，但一個人只收到一則：LINE 優先、email 墊底**（2026-10-13 廟方問「有辦法由 line 官方帳號發訊息通知信眾報名完成嗎」）。長輩每天在看 LINE、不一定看 email；但兩邊內容一樣，同時送就是同一件事講兩次。
  **能推 LINE 的前提是當初把 Login channel 建在與官方帳號同一個 Provider 底下**（為此整支重建過）：使用者 ID 綁 Provider 不綁 channel，不同 Provider 下同一個人是兩個 ID，官方帳號推不到登入時拿到的那個。**userId 存在 `auth.identities`（provider = `custom:line` 的 `identity_data.sub`），不必另開欄位**；用 service role 的 admin API 讀，與查備援信箱同一條路（所以設了 LINE 權杖時每個比對到的會員都要問一次 auth，沒設就只問需要備援信箱的那幾個）。
  **推不出去一定要退回 email**（沒加好友、封鎖、權杖過期）——不退的話那個人什麼都收不到，而後台看起來像已經通知了，這封信存在的理由就是讓信眾知道。退回成功**不算 error**，但要留一句 `備註`，廟方才知道這位信眾的 LINE 是斷的。
  **LINE 那則不要署名、不要「請勿回覆」、不要邀請入會**：官方帳號的對話框本來就知道是誰傳的、而且可以回覆；而收得到推播就表示他用 LINE 登入過、**本來就是會員**。本文兩邊共用一份（`bodyOf`），差別只在 email 的信尾（`mailTail`）。
  **`LINE_CHANNEL_ACCESS_TOKEN` 沒設就整個不推、email 照常**——LINE 是加分的那一層，不是必要條件。那是 Messaging API channel 的權杖（不是 Channel secret、不是 Login channel 的），**不加 `VITE_` 前綴**。
  **覆蓋率現在幾乎是零**：要用 LINE 登入過（才有 userId）又要加了官方帳號好友，而 LINE 登入 2026-10-13 才上線、報名又根本不需要帳號。推播另外要算官方帳號方案的訊息則數。

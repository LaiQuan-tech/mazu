# 公佈欄

- **公佈欄會自動收錄各服務的內容，廟方不必貼第二次**（2026-10-01：「要在祈福管理上架一次，又要在公布欄上架一次，有沒有辦法不要做二次工」）。作法在 `services/derivedBulletins.ts`。
  **是衍生不是複製**：一列都不往 `bulletins` 寫，前台讀公佈欄時把祈福活動、辦事日、誦經祈福、點燈項目即時轉成公告卡，與真正的公告合併排序。服務那邊上架／下架／改名，公佈欄立刻跟著變。代價是**這些卡的文案不能單獨改**（要改就改活動本身）——廟方 2026-10-01 在「自動出現」與「勾選同步後可編輯」之間選了前者。
  **場次類合併成一則**：辦事日、誦經祈福一場一則會把公佈欄淹掉，真正的公告全被擠下去；同一類合成一則、內文列近期場次（最多六場）。點燈同理——那是年年都在的常設服務，四種燈各一則會長期佔版面，而且時間戳刻意取最舊的讓它沉在底部。
  **衍生的卡一律 `isPinned = false`**：置頂是廟方用來把某一則壓在最上面的手段，衍生的卡若也能置頂就會把它擠掉。
  **同名的手寫公告優先，衍生卡自動讓位**（`DerivedSources.bulletins` 的 `written` 比對）：在這個功能之前廟方本來就替每個活動手貼過一則，不擋會出現兩張一樣的卡（實測「天赦日－點燈祈福」一度重複）。廟方哪天把舊公告刪掉，衍生的那張自己接上，中間沒有空窗。**標題不同的舊公告擋不掉**（例如「十月問事時間公佈」vs 衍生的「近期辦事日（問事）」），那要廟方自己清。
  **排序用的時間是「廟方什麼時候把這件事放上來」不是活動哪天辦**：誦經祈福第一版拿 `sessionDate` 當 `createdAt`，場次都在未來，那則就永遠壓在最上面。`RegularSession` 因此補了 `createdAt`。
  **報名走外部表單的活動不產生衍生卡**（`externalForm`）：卡片會帶「前往祈福登記」，而那對普渡那種活動是錯的入口。

- **公佈欄分成「首頁精選」與「完整清單」兩處（2026-10-11，廟方：「如果公布欄變多了，要怎麼呈現？」）**：首頁 `#bulletin` 只放**總共 4 則、置頂的算在內**（`HOME_BULLETIN_TOTAL`，2026-10-30 從 3 改成 4），底下一顆「查看全部公告（還有 N 則）」到 `/bulletins`。手機上每張卡 106px，不設限的話 15 則就是約 2000px、兩個半螢幕，信眾要滑過整面公告才走得到「關於我們」。
  **則數與欄數要一起看，不然最後一列會空一格**（2026-10-30 廟方：「直立平板時，應該要顯示四個活動」）。公告改成海報 banner 之後 `sm` 以上是格狀排版，而**平板直立是兩欄**——3 則就一定在第二列空一格，而且那一格正好落在畫面正中間。改成 4 則剛好排滿 2×2。
  **手機的自動輪播 2026-11-09 才真的會動**（廟方回報「沒做出來」）：程式原本就有，但 `onPointerDown` 一碰就永久停——往下滑整頁時手指常落在 banner 上；開了「減少動態效果」也整個不輪播。現在只有**左右滑這一排或按點**才暫停 10 秒（`RESUME_MS`）後恢復，減少動態效果改成 `instant` 直接切換。**間隔同日從 8 秒改成 4 秒、再改成 2.5 秒**（廟方：「等不到 8 秒就滑走了」「四秒太久了，改 2.5 秒」）。
  **換張的滑動是自己用 requestAnimationFrame 推的（`slideTo`，0.7 秒 ease-in-out），不交給 `scrollTo({ behavior: 'smooth' })`**（同日廟方：「目前滑動，沒有動畫，可以絲滑一點嗎？」）——開了減少動態效果的手機會直接跳過去，有些 iOS 對 snap 容器的平滑捲動也一步到位。動畫期間要**關掉 snap**（否則每一格都被吸回原地）、**不回推指示器**（否則點會閃回上一張），並有一支 `SLIDE_MS + 150` 的保險絲：畫面在背景時 rAF 會停，不能讓 snap 一直關著。
  **預覽視窗在背景時 rAF 是每秒 0 格**（`document.visibilityState` 卻是 visible），驗動畫要把 `window.requestAnimationFrame` 換成 16ms 的 setTimeout 再量。**驗證時預覽視窗本身就是減少動態效果**，所以那一條在這裡是預設會被驗到的。
  **欄數跟著則數走**（`COLS`，`components/BulletinBanners.tsx`）：4 則 → `sm:grid-cols-2 lg:grid-cols-4`、3 則 → `sm:grid-cols-3`、2／1 則 → 就那麼多欄。3 則以下只在廟方某一則沒放海報時才會發生（沒海報的那則走下面的 `BulletinCard`）。
  **桌機四欄要把那一排放寬到 `lg:max-w-6xl`**：塞在內文的 `max-w-4xl`（896px）裡每張只剩 **209×140**，海報上的字整個看不到＝又變回縮圖。放寬後是 **273×182**，與改版前三欄的 285×190 幾乎一樣大，而且一列放得下四則。**下面的內文與卡片維持 `max-w-4xl`**——那是閱讀寬度，1152px 的中文內文太長。
  量到的結果：平板直立 800 → 2×2 各 `366×245`；1024 → 一列四張 `225×151`；1280 → 一列四張 `273×183`；手機 375 → 輪播四張 `295×197`、四顆點。四種寬度都沒有水平溢出。
  **4 這個數字是看了實際畫面才定的**：2026-10-11 廟方說「最新用 5 則，不要 4」，隔天看到線上（當時 1 則置頂＋5 則＝6 張）後改回 4——**置頂的不計入上限**，所以 5 則的設定實際會長成 6 張。討論上限時要連置頂一起算給廟方看。
  **置頂不佔那 5 個名額**：廟方把一則置頂就是要它一直在最上面，被「最新 5 則」擠掉等於那個功能失效。
  **更多鈕要把數字講出來**（「還有 11 則」）——「查看全部公告」看不出值不值得點。少於等於上限時整顆不出現。
  **分類篩選只在 `/bulletins`**：首頁只有幾則，篩下去常常是空的。獨立頁的篩選鈕帶各分類的筆數，0 筆的分類不顯示。
  **參考武德宮但沒有照抄**：他們首頁是五行純文字（日期＋分類＋標題）、沒有圖也不展開，點 READ MORE 進一覽表。那對他們合理（標題就講完了），但**我們的公告是整篇 LINE 貼文加一張直式海報**，一行標題看不出是什麼、信眾要多點一次才知道要不要看。所以保留就地展開，而且 2026-10-30 起**海報直接攤在卡片上**（見下面那條），不再是縮圖。
  **卡片抽到 `components/BulletinBody.tsx` 共用**（`BulletinCard`）：同一則公告在兩邊必須長得一樣。**不可以留在 App.tsx 讓 `/bulletins` 反向 import**——App 懶載入那一頁、那一頁又回頭要 App 的東西，是循環相依。
  **單則公告有自己的網址 `/bulletins/<id>`**：廟方要把某一則貼到 LINE，以前只能貼首頁連結讓人自己找。展開時用 `replaceState` 換網址（**保留原本的 query**，`?preview=1` 這類掉了重新整理會變一種行為）。
  **深連結要捲兩次，而且用 instant 不用 smooth**（2026-10-11 實測踩到）：瀏覽器在 load 完成後會還原捲動位置（`history.scrollRestoration` 預設 `auto`），而我們是在資料回來時就捲的、比 load 早，**第一次捲的結果會被還原成 0 蓋掉**——症狀是卡片確實展開了但頁面停在最上面，等於這個功能白做。不要改全域的 scrollRestoration（會動到其他頁按上一頁的行為），改成在 load 前後各補一次；已經在畫面上就不再捲，免得使用者這 0.7 秒內自己滑走又被拉回去。
  **分享卡片仍是整站那一張**：單則的 og 標籤要為每一則產一份靜態 HTML，而公告是資料庫來的、發佈當下不會重新建置。連結會落在正確的公告上，但預覽圖文是通用的——**這是已知取捨不是漏做**。
  **祈福的衍生卡會直接開那一場的報名表**（2026-10-23 廟方：「不要到祈福活動頁，直接進入報名表單，增加轉化率」）。衍生卡多帶一個 `linkedEventId`（**只有衍生卡有，不是資料庫欄位**——廟方手寫的公告不知道自己在講哪一場），`onService(svc, eventId)` 拿得到就 `goToPage('blessing')` ＋ `openBlessingModal(ev)`。
  **還是要先換頁**：報名彈窗的 JSX 掛在 `page === 'blessing'` 底下，只設 state 不換頁不會渲染；而 `goToPage` 不會清掉 `blessingModal`，所以兩件事一起做就好，不必另做 pending ref。
  **找不到那一場就退回原本的換頁**（已下架、資料還沒載完）——寧可多一次點擊，也不要按了沒反應。問事／點燈那些沒有 eventId 的卡行為完全不變。

  **衍生卡沒有自己的網址**：它是由服務資料即時算出來的，id 不是真的主鍵、內容每天都在變，給它固定網址只會指到一個會漂移的東西。
  **「連結服務」多一個「遷址募資」**（2026-10-23 廟方：「置頂的遷址募資，內容最後要加上按鈕導引去募款頁」）。這是後台的下拉選項，不是寫死在程式裡的——廟方自己在公佈欄管理把那一則的「連結服務」選成遷址募資就會出現按鈕。
  **加新的 `linkedService` 要動四個地方**：`types.ts` 的 union、`App.tsx` 的 `SERVICE_PAGE`（**型別綁死成「每一種都要有頁」，漏補是編譯錯誤**）、`BulletinBody.tsx` 的 `SERVICE_CTA`、後台那個下拉與 `serviceLabel`。
  **按鈕文案一個服務一句話，不要用「前往」＋標籤拼**：拼出來的「前往遷址登記」不通，那一頁要做的事叫護持不叫登記。
  **`bulletins.linked_service` 可能有 CHECK**（那一欄的 DDL 不在 repo，是當初在後台手動建的）。`bulletin_linked_service_relocation.sql` 會先查再改：有約束就換成含 relocation 的新版，**沒有就什麼都不做**——原本沒驗證就維持原狀，硬補一條只是替日後多立一個「忘了跑 migration 就存檔失敗」的關卡。

- **手機選單的順序是：社群 → 會員中心 → 天上聖母經 → 導覽項目 → 次要項目**。會員中心原本在最底下，項目一多就被 `max-h-[80vh]` 推到要捲動才看得到。**會員鈕要放在社群的條件式之外**——後台把社群清空時 `visibleSocials` 回傳空陣列，會員入口不能跟著消失。

- **首頁長度 2026-10-23 砍掉三分之一**（廟方：「首頁，我想再短一點」）。先量再改，手機 375×812 從 11,847px（14.6 屏）降到 8,002px（9.9 屏）；桌機 7,188 → 6,330。四件事，**每一件都只動版型沒有刪內容**：

  **`lg` 以上一個像素都沒變**（除了捐獻那一塊）：桌機神尊本來就是四欄一列，照片與內距都走 `sm:` 保留原值。
  **量的時候要用 in-app 導覽走到首頁**：localhost 與 machu-five 都不是 `OFFICIAL_HOSTS`，直接開 `/` 會被法會著陸頁蓋掉（見 `shouldShowFahui()`），量到的是另一頁。
  **神尊卡片的 `compact` 只給首頁**：卡片是與 `/deities` 共用的，首頁兩欄時只剩 163px 寬，`p-6` 吃掉四成、六行介紹變成每行八個字的碎塊；`/deities` 是「把 38 尊看完」的那一頁，不能跟著收。
  **隨喜捐獻先搬頁、再整區移除，分兩步做的**。中間那一版首頁留了一張 CTA 卡（標題＋一句話＋「我要隨喜護持」，341px），廟方看了之後說「直接從首頁刪除」——**現在首頁一個字都沒有**。
  **搬頁要連帶五件事**，少一件就有一個入口會斷：`SitePage`／`PAGE_PATHS`／`titles` 三處登記、`NAV_MORE` 的 `kind` 從 `section` 改成 `page`、`SERVICE_PAGE` 補 `donation`。
  **整區移除之後還要收三個尾**：捲動高亮的對照表（`pairs`）裡那一筆要拿掉（首頁已經沒有 `#donation` 這個元素）；`#faq` 的紋樣從龍右換成**鳳左**——它原本接在隨喜捐獻（鳳左）之後，上一塊沒了就直接接 `#bulletin`（龍右），不換邊就連兩塊同一側；還有兩處註解裡指名 `#donation` 當範例的要改掉。
  **首頁現在唯一的捐獻入口是導覽列「更多」裡那一項**（＋ `/donation` 這個網址、sitemap 與 llms.txt）。這是廟方 2026-10-23 明確的決定，不是漏做——我提過轉化率的疑慮，廟方兩次都選了移除。
  **`SERVICE_PAGE` 的型別順手改成 `Record<NonNullable<BulletinRecord['linkedService']>, SitePage>`**：四種 linkedService 現在都有自己的頁，呼叫端那條 `onNonPage` 退路（捲去首頁 `#donation`）已經移除；日後再加一種服務而忘了補，編譯就會擋下來，不會變成「按了沒反應」。
  **獨立頁的大標要用 `h1`**（2026-09-04 那次「四個服務頁一個 h1 都沒有」的教訓）：`/donation` 用 `h1`。實測首頁與 `/donation` 各剛好一個 h1。
  **llms.txt 與 prerender ROUTES 都要補一筆**，而且要寫明「捐獻有兩種、帳戶不同」——AI 被問到「要捐錢給和聖壇」時會把遷址專款與一般護持混在一起答。

- **Hero 的香煙 2026-10-16 關掉了**（`ENABLE_INCENSE_SMOKE = false`，廟方要求「hero把煙拿掉」）。**用旗標不刪檔案**，照 ENABLE_REPAIR／ENABLE_BULLETIN 的模式：那支元件累積了好幾輪廟方回饋才調出來（一炷香→一爐多縷→香粉，縷數與擴散參數都是量畫布像素定的），砍掉等於把下面那幾條結論一併丟了，而要回來只是把那一行改成 true。

- **Hero 香煙（`components/IncenseSmoke.tsx`）**：**畫一條會捲的曲線，不要用粒子**。第一版做粒子模擬，粒子一散開單顆濃度就掉到看不見，整體只剩一片霧——廟方要的是「細細長長的一縷白煙」，粒子做不出來。三個關鍵：(1) **螺旋要 x、y 同時繞**（`COIL`）——只讓 x 擺動、y 單調往上，畫出來是鋸齒像閃電；真實的煙是繞著上升軸的螺旋，側看會投影成一串壓扁的橢圓、甚至自我交疊，那才是麻花感。(2) **擾動隨高度才加進來**（`LAMINAR`/`TRANSITION`），下段直、上段捲，這是線香層流轉紊流的真實行為。(3) **柔邊靠疊四道**（`PASSES`）由寬而淡到窄而濃，只畫一道不是銳利得像鐵絲就是糊得像霧。形狀的相位隨時間往上跑、速度等於煙速（`RISE_SECONDS` 換算），煙的形狀是被氣流整段帶著走的。線很細所以要照實際像素畫，用一半解析度會糊掉。(4) **整條一次 `fill()`，不要分段 `stroke()`**——舊版把曲線切成 40 段各自描邊，`lineCap:'round'` 讓每段的圓頭與下一段重疊、螺旋自我交疊處又再疊一次，alpha 相加就是一串「反光顆粒」（離線量到沿線 35 個亮點，接近 240/6=40 個接縫）。改成沿中心線推出半個線寬、繞一圈成封閉多邊形整條填滿：沒有接縫，而且 nonzero 填充規則對自我交疊只填一次。濃度改用垂直線性漸層（`alphaAt` 只跟高度有關，剛好對得上）。改完亮點數降到 4、相鄰起伏降到 1/10；因為不再疊加，平均亮度掉 17%，`PASSES` 的 a 要乘 1.3 補回來。捲離 Hero 或切分頁會停掉 rAF；可見與否一律以 `getBoundingClientRect` 為準，不採信 IntersectionObserver 的 isIntersecting（誤報一次 false 就會永遠停住）。

- **Hero 左下角有一幅書法（2026-10-25 廟方提供原圖）**：「這個可以放在桌機版的左邊嗎？然後把黑色的字變成白色的字，讓畫面不要太空，平衡一點」。
  **只在 `lg`（1024px）以上出現。** 桌機左側確實空著，但**手機沒有那塊空間**——三尊神尊橫跨整個寬度，字標與神尊頂端之間只剩一條窄帶，塞進去就是壓在主神的冠帽上（同 2026-10-24 影片那次的量測，理由一字不差）。手機的 Hero 本來就是滿的，廟方說的「太空」講的是桌機。實測 1023px 與 iPad 直立 820px 都正確隱藏。
  **墨是白的不是黑的**（廟方指定）。原圖是黑墨白紙，**沒有寫成 `scripts/` 的腳本**，處理方式記在這裡以免日後換圖沒人知道怎麼做：**拿亮度當 alpha**（越黑越不透明）再把顏色填成白——紙會變成透明、筆畫變成白的。**不可以用「反白」**，那會連紙一起變成一塊白方塊。**印章保留原本的紅**（判斷式 `R - max(G,B) > 25`）：那是書家的落款，整張都白掉等於把簽名擦了。裁到內容邊界後就是 1337×1836（原圖裁完的全解析度，沒有再縮）。顯示最大 932（2560 寬），1920 時 2.0x、1440 時 2.76x。webp 285KB／png 570KB——**只有桌機會載，手機一個請求都不發**，輸出 **webp＋png**（要 alpha，jpg 不行），檔名列進 `HERO_FILES`。
  **手機完全不會下載它**：`hidden lg:block` 的 `display:none` ＋ `loading="lazy"`，實測 375px 下對這兩個檔是 0 個請求。這點對本站特別重要——信眾多是長者、網路不一定好，一張純裝飾的圖不該讓他們付錢。
  **白墨壓在金箔上一定要暗邊**：本檔記過金底白字只有 3.17:1，字標那組雙層 `drop-shadow` 正是為此存在的，書法沿用同一招（稍微放軟，筆畫比字標粗）。
  **左緣與字標對齊（`left-10`）、`z-20` 與字標同層**（神尊 z-10 之上、按鈕 z-30 之下），兩者左緣對齊才像同一個版面而不是飄進來的第二個元素。
  **手機也有，而且刻意讓神尊擋住下半截**（廟方 2026-10-25：「手機也要有」「神尊可以遮到」）。手機沒有「神尊左邊」那塊空間——三尊橫跨整個寬度（375 時 x −6 到 381），字標下緣 151 到神尊頂端 372 之間只有 221px。但既然可以被蓋，就不必整幅塞進那條空檔：擺大一點讓下襬沉到神尊後面（書法 `z-0`、神尊 `z-10`，本來就會被擋），露出來的上半截反而像字從神尊後面長出來。
  **桌機那組一定要有 `lg:left-auto`**：絕對定位的替換元素同時給了 `left` 與 `right` 時，**`right` 會被忽略**——不關掉手機的 `left`，桌機「右緣貼著神尊」就整個失效，而且畫面上只是位置怪、不會報錯。
  **手機是置中的、而且放大了一輪**（廟方 2026-10-25「字，也是大一點，置中」）：`left-1/2 -translate-x-1/2`，桌機要把**兩個都關掉**（`lg:left-auto lg:translate-x-0`）——不關 `left`，`right` 會被忽略、桌機「右緣貼著神尊」整個失效；不關 `translate`，整幅再往左位移一半寬度。兩者在畫面上都只是位置怪、不會報錯。
  **量過（手機／平板，括號是放大前）**：375×812 `307×422` 露出 61%（247×340）、360×640 `242×333` 露出 45%、430×932 `313×430` 露出 57%、768×1024 `313×430` 露出 35%——平板的神尊是用 `vh` 算的、特別高，所以蓋得最多。**這一檔 2026-10-30 已經處理掉**（見下一條）。

- **`md`（768–1023）要單獨給一檔，不能照用手機的尺寸**（2026-10-30 廟方：「桌機，不再全螢幕時，背景書法應該要再大一點」）。把視窗從全螢幕縮回來，寬度常常落在 800–1000：`lg` 那套靠右貼神尊還沒生效，就整個退回手機的 `min(52vh,430px)`。**實測 850×580 只有 220×302**，在那麼大一片金箔上像一張貼紙。
  **只能往下長不能往上**：同一次實測上緣已經在 y=81，而導覽列佔 70px，再往上就壓到導覽列的白字（金底白字只有 3.17:1，見上面）。所以 `md:bottom-0 md:max-h-[calc(100vh_-_70px)]`——**垂直方向與 `lg` 同一套**。
  **水平也不要置中，要從字標右邊起算**（同日廟方：「這種螢幕尺寸，書法就要靠左邊，因為左邊還有空間」）。視窗一矮，書法的寬度是被**高度**決定的（高 × 0.728），置中就會在左邊留一條空的金箔：875×592 實測書法左緣 247，而字標「和聖壇」右緣只到 100，中間 147px 整片空著。改成 `md:left-[120px] md:translate-x-0`——**120 ＝ 字標右緣 100 再留 20**，而字標是固定字級（`sm:text-6xl`），整個 `md` 區間都是同一個數字。刻意不與字標水平重疊，白墨壓白字那一題就不會發生。
  **`md:max-w-[calc(100vw_-_140px)]` 是配套不能省**：靠左之後寬度不再兩邊均分，窄的那一端（768）書法本來就幾乎佔滿寬度（628／768），從 120 開始會超出右邊被 `overflow-hidden` 切掉。夾住之後它就是「從字標右邊鋪到離右緣 20px」，高視窗吃寬度、矮視窗吃高度，兩邊都不出框。
  **不設 px 上限，被神尊蓋住也沒關係**（廟方同日：「書法字要大才有氣勢，被神尊遮住都沒關係」）。第一版留了 560px 上限怕平板直立太大，廟方直接否掉——它是背景不是插圖，露出來那截夠大才有氣勢。
  量到的結果（靠左之後）：875×592 → `380×522`，左緣 120、離字標 20；768×1024 → `628×862`，左右各留 20；1023×700 → `459×630`。改版前 850×580 是 `220×302`、768×1024 是 `313×430`。1280×800 的 `lg` 一格沒動（`531×729`，右緣 739 ＝ 算式值），手機 375×812 也沒動（`307×422` 置中）。四種寬度都沒有水平溢出，長寬比一律 0.728。
  **白字壓白字在手機也量過**：字標方框與書法相交時，相交區內的不透明筆畫是 **0.0%**（375 與 360 都是），所以「和聖壇」仍然清楚。
  **靠右貼著神尊，不是靠左**（廟方 2026-10-25：「要靠右，靠近神明，最大，字就是背景圖」）。前幾版是 `left-10`／`xl:left-32` 靠左長，結果字與神尊之間空一大片金箔。現在是**右緣鎖在神尊左緣前 6px**，高度吃滿，往左自然長。
  **右緣與寬度都用算式算出神尊左緣，絕對不要用 `vw` 猜**（2026-10-25 第三輪才修對）。神尊那一組是**靠右**排的（不是置中），尺寸全部以 `min(100vh, 110vw)` 為單位（見 `HERO_DEITIES` 的 `land:` 值）：

      神尊左緣 = 100vw − 24px − 0.886 × min(100vh, 110vw)

  所以 `right` ＝ `calc(0.886*min(100vh,110vw) + 30px)`（24 ＋ 6 留白）。這條式子在 1024×768／1280×800／**1280×1024**／1440×900／1920×1080／1366×640 六個尺寸上都準（319／547／**349**／618／939／774）。
  **為什麼非這樣不可**：神尊的大小跟著**視窗高度**走，用 `vw` 當上限在「同寬不同高」的視窗上必然失準——**1280×1024 的神尊左緣是 349，而 1280×800 是 547**，用 vw 的那一版在那裡疊到神尊 84,463px²，而 1024／1280／1440／1920 四個常見尺寸全部正常。**驗收一定要測同寬不同高的那一組**，不然這種錯會一路上線。
  **`z-0` 是關鍵，不是隨便挑的**（廟方 2026-10-25：「像神尊碰到漸層一樣」）。Hero 底部那道收邊（`.hero-bottom-fade`）的 z-index 是 **`auto`**，而**有 z-index 的定位元素一律畫在 auto 之上**——所以寫 `z-[5]` 時書法是畫在收邊**上面**的，往下長只會被 `overflow:hidden` 切出一條硬邊、不會化掉。改成 `z-0` 之後它與收邊同層、照 DOM 順序畫（書法在前、收邊在後），收邊就蓋得到它，下襬自然化進紙裡——跟金箔底一樣。
  **神尊是另一套機制，不要混在一起想**：那一層是 `z-10`，畫在收邊**之上**；它們的下襬會淡出是因為**圖檔本身做了淡出**（2026-09-02 的 changelog），而且它們是**超出 Hero 底部** 54–108px 再被 `overflow:hidden` 切掉的。所以「看起來都在碰漸層」的兩個東西，做法完全不同。
  **白字壓白字要實際量「有沒有墨」不是量方框**。書法吃滿高度之後左緣會到 x=10，整個穿過「和聖壇」。實測字標區內的不透明筆畫：1024×768／1280×1024／1920×1080 **無重疊**，**1440×900 是 15.3%**（「就」那一撇掃到「壇」的右下）。
  **撐住可讀性的是字標那組雙層 `drop-shadow`**（`0 1px 2px rgba(0,0,0,.95)` ＋ `0 2px 8px rgba(0,0,0,.6)`）——它本來就是為「白字壓在亮色墨上」做的（見墨流那一段，當時金最亮處與標題量到 1.05:1）。**所以不要為了好看把那圈暗影拿掉或調淡**，它現在真的在工作。

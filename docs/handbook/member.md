- **會員一定是信眾，信眾不一定是會員**（廟方 2026-10-24 講明）。`member_profiles` 本身就是信眾名冊的一個管道（`'會員'`），所以每一個會員都會出現在「信眾資訊」裡；而報名與點燈都不需要登入，名冊上絕大多數的人沒有帳號。信眾人數那張卡會註明「其中 N 位有會員帳號」，拿去跟「會員資訊」的人數對照——對不起來就表示有會員報名時填的姓名與帳號上的不一樣（名冊以姓名彙整，用「比對併入」處理）。
  **「是不是會員」要看 `isMemberSelf`／`memberAccounts`，不可以看有沒有編號**（2026-10-24 修）。`member_number` **是廟方自己給的、程式從頭到尾不寫它**（全 repo 沒有任何一處 insert／update 那一欄），所以沒編號的帳號是正常存在的——會員管理那邊本來就印得出「（無編號）」與「—」。而信眾名冊原本兩個地方都拿編號當判準（列表的徽章、`linkMembersByPhone` 的建表），**未編號的會員於是在這一頁上看起來完全不是會員**：管道欄寫著「會員」、帳號欄卻是「—」，自己跟自己矛盾。
  **帳號欄有三種來源，可信度不同，畫面上要分得出來**（`AccountCell`）：
  | 來源 | 可信度 | 樣子 |
  |---|---|---|
  | 這一筆就是帳號自己的資料（`會員` 管道） | 事實 | 實心 |
  | 這個人在某個帳號的通訊錄裡 | 事實，但他**不是**帳號本人 | 實線框＋「的通訊錄」 |
  | 只用電話對到的 | **推測** | 虛線框＋「同電話」 |
  **通訊錄那一條是把本來就知道的事實撿回來**：`member_contacts` 綁 `user_id`，誰的通訊錄查得到，原本卻被丟掉改用電話猜——而家人那幾筆根本沒有電話，猜也猜不到，整欄顯示「—」。
  **「對到的正是自己的帳號」要另外標「本人」**：不分開的話，「他自己的點燈」與「兒子借媽媽電話報名」在畫面上長得一模一樣，虛線想警告的那一種就被稀釋掉了——而那正是這個標示唯一存在的理由。
  **已知限制**：好幾個未編號帳號共用「未編號會員」這個代稱，分不出是哪一個。要分得出來就得去會員管理把編號補上，而那正是這個標示想促成的事。

- **報名不需要會員帳號，所以「會員管理」看不到報名的信眾**（廟方 2026-10-13 問起）。四個表單（＋法會）對未登入的人是開放的，只要留一支電話就送得出去（`member ? memberProfile.phone : guestPhone`），程式不會也不該替他建帳號。**要看所有來往過的人去「信眾資訊」**（`devoteeRoster`，八個來源以姓名彙整，沒有「會員」標籤的就是報了名沒註冊的）。
  **不要做「自動幫報名者開帳號」**：手上只有姓名與**未驗證**的電話，開出來的帳號他本人登不進去；而真要用電話自動配對，等於任何人填別人的號碼就能接收對方的通訊錄與揪團名單（同帳號合併走「綁定」而不走自動合併的理由）。
  **沒有帳號不影響紀錄**：報名紀錄一律以電話為鍵（`my_phone()`），他哪天註冊、填上同一支電話，過去的點燈問事捐獻法會就會自己出現。
  **確認信／感謝信末尾會邀請還不是會員的人加入**（`MEMBER_URL = https://heshengtan.tw/?member=1`，那個參數會讓會員中心自己打開）。成功頁那顆「立即加入會員」只有一瞬間，而這封信他會留著，又是廟方剛確認完、他正放心的時候。**已經是會員的不寄這段**（拿電話對 `member_profiles`，同一封信裡只要有一位是會員就整段不出現——寧可少講一次也不要對著會員喊話）。信裡**「請留同一支電話」是最有用的一句不是客套**：電話對得上舊紀錄才接得起來，填別支他不會知道為什麼接不上。也要點名 LINE——長者的門檻是記密碼，「不必記密碼」才是他會按下去的理由。
  **那 9 位反映的是「email 密碼時代」**：LINE 登入 2026-10-13 才上線，在那之前按下去看到的是「填 email、設密碼」，那正是會放棄的一關。

- **會員管理一個人只列一次，不是一個帳號一列**（`MembersTab` 的 `toPersonKey`，2026-10-13 廟方回報清單上有三筆「鍾介凡」、數字一模一樣）。
  **數字一樣不是程式把金額複製過去**：這一頁的統計全部是拿電話去對報名紀錄的（`l.phone === p.phone`），三個帳號填同一支電話，所以是同一筆 NT$2,500 被顯示三次——錢沒有重複計算，是「人」被列了三次。**統計層早就把他們當同一個人，只有列表層還當成三個**，這次是把兩邊對齊。
  一個人會有好幾個帳號：用信箱註冊過一次又用 LINE 登入一次（LINE 不給 email，Supabase 只能開新帳號），或 LINE 的 Provider 換過（使用者 ID 綁 Provider 不是綁 channel）。正解是本人到會員中心「綁定 LINE 帳號」，**但已經各自存在的帳號合併不了**，所以後台至少要看得懂它們是同一個人。
  **合併條件刻意收得很緊：電話與姓名都要一樣。** 只看電話會把共用一支號碼的家人併成一個人（長輩常留子女的號碼），那是把一位真的會員藏起來，比列重複嚴重得多；**電話空白的一律不併**，否則所有「LINE 登入後還沒補電話」的帳號會被併成一團。實測這兩種情況都不會被誤併。
  代表那一筆取**最近登入**的（顯示的姓名性別才是最新的），但「加入」取**最早**的帳號——照代表帳號顯示的話，2024 年入會的人會變成「今天加入」，預設排序也會把他推到最前面。
  **通訊錄要逐個帳號抓**：`member_contacts` 綁 `user_id`，一個人有三個帳號時家人名單散在三邊，只抓代表那個會看到殘缺的名單而且看不出有缺。
  標題的數字**數的是人不是帳號**，兩者不一樣時才把帳號數講出來。
  （信眾名冊那一頁本來就是以**姓名**彙整的，三個編號會收進同一列，不受這個問題影響。）

- **會員在會員中心存檔後，App 那份 `memberProfile` 要跟著更新**（2026-10-13 修）：自動帶入吃的是 App 的 `memberProfile`，那是登入當下抓的；會員存檔動到的是資料庫，不通知就一直是舊的——**報名表於是永遠沒東西可帶，要整頁重新整理才會好**。
  修法是 `MemberPortal` 的 `onProfileSaved` 回呼，**存檔當下就通知**；只在 `onClose` 重抓擋不住「存完直接從會員中心的揪團連結跳走」。
  **這個 bug 藏很久才被發現，因為信箱註冊的老會員早就填過資料看不出來**；LINE 登入的人 100% 會遇到——全新帳號、profile 是 null，而動線必然是「登入 → 馬上補資料 → 去報名」。新增這類「資料在別處被改」的流程時，想一想 App 手上那份快取誰負責更新。

- **LINE 帳號登入（`services/lineAuth.ts`，2026-10-13 建置並上線實測成功）**：信眾以長者居多，記 email 與密碼是真實的門檻；LINE 在手機上會跳進 App、按一下「允許」就回來。
  **Supabase 沒有內建 LINE**——社群那個 PR（supabase/supabase#46920）2026-09-23 被關掉、沒有合併。走 2026-02 開放的**自訂 OAuth 供應商**，**型別要選 OAuth2 不是 OIDC**：LINE 網頁登入的 ID token 是 HS256 簽的，自訂 OIDC 拿 JWKS 驗章驗不過；OAuth2 型別不碰 ID token，改打 LINE 的 userinfo 端點。設定步驟寫在 `lineAuth.ts` 檔頭。
  **實際設定（已完成，供日後重建參考）**：LINE Login channel 的 Channel ID `2011983862`（Channel secret 在 Supabase，不在 repo）。
  **這個 Login channel 必須與和聖壇官方帳號的 Messaging API channel 在同一個 Provider 底下**——LINE 規定兩者同 Provider 才連得起來（登入時順便加好友的 `bot_prompt`）。2026-10-13 第一版建錯在 `ChuMe` 底下（channel `2011983641`），下拉選單裡選不到官方帳號，整支重建過。
  **換 Provider 等於所有人的 LINE ID 全部改變**：LINE 的使用者 ID 是**綁 Provider 不是綁 channel**，同一個人在不同 Provider 下拿到不同的 ID。所以重建時已經用 LINE 登入過的帳號會全部對不上——**要換就趁還沒有信眾用的時候換**。附帶好處：同 Provider 之下，登入拿到的 ID 與官方帳號看到的 ID 一致，日後才可能用官方帳號對特定會員推訊息。
  其餘設定：Supabase 自訂供應商 Provider Identifier 填 `line`，**SDK 要呼叫 `custom:line`**（`custom:` 是 Supabase 自己加的前綴）；Configuration Method 選 **Manual configuration**；Issuer `https://access.line.me`、Authorization `https://access.line.me/oauth2/v2.1/authorize`、Token `https://api.line.me/oauth2/v2.1/token`、Userinfo `https://api.line.me/oauth2/v2.1/userinfo`、**JWKS URI 留空**、Scopes `openid, profile`、**Allow users without email 打開**。
  **Userinfo 不可以用 `/v2/profile`**：那支回 LINE 自己的 `userId`／`displayName`，Supabase 要的是標準的 `sub`／`name`／`picture`——這也是 scopes 必須帶 `openid` 的原因。
  **`redirect_to` 帶 query string 時，Supabase 的 Redirect URLs 要有萬用字元**（`https://heshengtan.tw/**`，兩個星號），否則 `?member=1` 那個網址會被擋掉。
  **最難查的一個坑：自己的程式把網址的 hash 砍掉**（2026-10-13，花了三輪才找到）。supabase-js 預設 implicit flow，登入成功的 token 放在 `#access_token=…` 裡；而 App.tsx 處理 `?member=1` 的那支 effect 重組網址時只接了 pathname 與 query，**等於在 supabase-js 讀到之前把整個 hash 砍掉**。症狀是「繞一圈回來沒登入、沒有任何錯誤訊息、網址乾乾淨淨」，看起來像迴圈——**因為不是錯誤，所以哪裡都查不到**。任何會 `history.replaceState` 的程式都要把 `window.location.hash` 原樣帶回去。
  **`ENABLE_LINE_LOGIN` 是唯一的防線不是保險**（實測）：供應商還沒建好時 `signInWithOAuth` **不回傳錯誤**，而是直接把瀏覽器轉去 Supabase、落在一頁英文 JSON（`Unsupported provider`），`signInWithLine` 裡的錯誤處理完全不會執行。Supabase 那邊確認可登入之前一定要維持 false。
  **LINE 只回 userId／暱稱／頭像，沒有 email 也沒有電話**，由此衍生三件事：
  (1) `currentUser` 不能假設有 email——原本三處寫 `setCurrentUser({ email: user.email })`，LINE 帳號會整個登入不進來；改走 `describeUser()`，退到暱稱再退到「會員」。
  (2) **報名紀錄是拿 `profile.phone` 去對三張表的**（`loadRecords`），所以登入後沒電話要引導補；信箱註冊沒填電話也是同樣的空畫面，提示不分登入方式都給，且要等 `profileLoaded` 才判斷否則會先閃一下。
  (3) 轉址回來帶 `?member=1` 讓會員中心自己打開，否則信眾覺得「按了登入什麼都沒發生」；參數用完要清掉，**其餘 query 要保留**（`?share=` 掉了那張揪團表就不見了）。
  **`bot_prompt=normal` 實測傳得過去**（產生的網址帶著它），同意畫面可順便加官方帳號好友——要先在 LINE Developers 把官方帳號連到那個 Login channel。
  **帳號合併＝綁定（identity linking），不是用電話自動併**（2026-10-13 廟方要求做合併）：手機是會員自己在個人資料打的、**沒有任何驗證**，自動合併等於任何人填別人的號碼就能把對方的通訊錄（家人的姓名生日地址）與揪團名單併過來。`member_profiles`／`member_contacts`／`shared_sessions` 現在都是 `user_id = auth.uid()` 嚴格隔離的，不要親手打開這個洞。（報名紀錄本來就以電話為鍵——`my_phone()` 讀的就是自己填的那個電話——那是**既有的弱點**，但不該再擴大。）
  正解：先用原本的信箱密碼登入證明身分，再在會員中心按「綁定 LINE 帳號」（`linkLineAccount`）。接上後用 LINE 登入就是同一個 user id。**要先在 Supabase 後台開「Allow manual linking」**，預設是關的。
  **兩個踩很久的坑**：
  (1) **OAuth 的 `error_description` 要在進站那一刻就抓**——supabase-js 的 `detectSessionInUrl` 會自己把回呼參數從網址清掉，懶載入的元件掛載時再讀一定是空的。快照 `ENTRY_URL` 放 `attribution.ts`（App 啟動就載入），**不能放 `lineAuth.ts`**（它是被懶載入的會員中心帶進來的）。
  (2) **StrictMode 會把 effect 跑兩次**，而 `takeAuthErrorFromUrl()` 只回傳一次：無條件 `setLinkError(...)` 的話第二次拿到空字串、剛讀到的訊息又被自己洗掉。要 `const e = …; if (e) setLinkError(e)`。正式站沒有 StrictMode，所以**只有本機看得出來**。
  錯誤訊息**未登入時也要顯示**：LINE「登入」失敗（不是綁定）的人回來就是未登入狀態，只畫在已登入區塊等於「按了沒反應」。

- **信眾表格預設只給五欄**（2026-10-30 廟方：「這張表很長，後台操作不易」）：姓名／電話／最近參與／參與管道／操作——正好是「找人 → 看他最近有沒有來 → 直接代報名」那條動線。關係／性別／地址／累計金額／可能親屬收在「更多欄位」開關後面。
  **收起不是刪掉**：點「檢視」照樣看得到每一筆原始紀錄，**匯出 Excel 也一律是全欄位**，不跟著開關走——匯出是拿去對帳與列印的，少一欄比多一欄糟。
  改欄位時**表頭與表身是兩個地方、順序必須一致**；只改一邊的話整張表會錯位一格，而 React 不會報錯。
  （2026-11-18 起）那四欄（關係／性別／累計金額／可能親屬）**一律輸出**，`showMore` 為 false 時表頭與表身都加 `lg:hidden`——桌機照舊由開關決定，手機卡片改由每張卡的「更多資料」展開，開關本身只在桌機出現。**地址已移出這一組**，改由姓名格的「地址」鈕就地展開（見下一條）。**電話、最近參與 2026-11-18 也收進同一顆鈕**（改名「個人資料」，廟方：「電話可以收折」「最近參與可以收折」），表格不再有這兩欄；**關係寫通訊錄主人的姓名**（「李沛玲的兒女」，`relationOf.who`；廟方：「#1041 的兒女」不知道是誰），帳號沒填姓名才退回編號；搜尋照樣比對電話，匯出照樣有電話欄。

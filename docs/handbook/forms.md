- **報名送出的 insert 走 `insertOptional()`，選填欄位遇到 schema 不符就捨棄重送**（`services/supabase.ts`，2026-10-13）：本專案所有 DDL 都是人在 Supabase 後台手動跑的，程式與資料庫之間必然有時間差——而且那不是「幾分鐘」的事，**廟方後台那顆「重新發布」會從 git 重建正式站，程式隨時可能比 migration 先上線**。那段時間裡少一個選填欄位（如 `email`）就讓四個表單全部送不出去，代價完全不成比例。
  **只捨棄錯誤訊息真的指名的那幾欄**：不比對名字就等於「schema 一有問題就把選填欄位全丟掉再送」，而真正缺的若是必填欄位，第二次照樣失敗、錯誤訊息卻換成第二次那個，查起來會指向錯的方向。實測三種情況：缺 `email` → 兩次、第二次不帶就過；缺 `birth_date` → 只試一次並原樣拋錯；正常 → 一次。
  只在 PostgREST 的 `PGRST204`（schema cache）這一類才重試，所以**不會有重複寫入**：那種失敗根本沒碰到資料。
  **一輪只退一欄是不夠的**（2026-10-23 修）：PGRST204 的訊息一次只指名**一個**欄位，而原本的寫法「退一次就放棄」——只要資料庫同時缺兩欄以上，第二次照樣失敗然後拋錯，**整張表單送不出去**，正好是這支函式存在要避免的事。在那之前只有 `email` 一欄是選填的，所以這個缺陷一直沒有顯現；遷址護持一口氣加了三欄才踩出來。現在是迴圈，上限就是選填欄位的數目（每一輪至少刪掉一欄，不會空轉）。
  **實測**：三欄全缺時送出成功，console 一行印出 `birth_date／relocation_plan／relocation_tier`。

- **id 一律用 `newUuid()` 不要用 `crypto.randomUUID()`**（`services/supabase.ts`，2026-10-11）：後者要 Safari 15.4（2022-03）以上，而本站信眾以長者居多、舊手機比例不低。2026-10-11 把六個報名表的 id 改成客戶端先產之後，這個呼叫就落在**必經路徑**上——沒有退路的話舊機子按下送出會丟 TypeError，整筆報名失敗而且畫面只顯示「送不出去」。`newUuid()` 退到 `getRandomValues` 照 RFC 4122 v4 組字串（實測 2000 組格式全合法、無重複）。檔案裡 13 處都已換掉。
  **為什麼 id 要客戶端先產**：anon 只有 INSERT 權限、不能 `.select()` 讀回（見 Supabase 陷阱那張表），而要通知廟方「是哪一筆」就得先知道 id。實測帶著 id 寫入 `bookings` 回 201，RLS 不擋。

- **生日輸入全站只有一種**（2026-08-13 統一）：預設國曆，旁邊一行「我只知道農曆」是給不記得國曆的長者的次要入口。**兩條路徑輸出完全相同的合併字串**（`民國72年6月20日（農曆五月初十）`，跨年時農曆會多帶年份），所以資料庫裡只有一種格式。`solarOnly` prop 已移除。

- **會員資料自動帶入**（App.tsx 的 `selfDefaults`／`selfWithBirth` ＋ 那支 effect）：已登入且填過會員中心資料時，**標記為「本人」的那張卡片**自動帶入姓名／生日／生肖／性別／地址；其他人的卡片只帶地址。四個表單（問事／點燈／祈福／捐獻）共用同一套，送出後重置也會重新帶入。兩個必須遵守的細節：(1) **只補空欄位**，使用者改過的一律不動，沒有變動時 `fillEmptyFields` 回傳原參考避免多餘重繪；(2) **帶入生日一定要遞增 `_bKey`**——`BirthDatePicker` 的年月日是內部 state，只在掛載時從 value 初始化一次，光改字串畫面不會動（三個下拉會停在「吉年／吉月／吉日」）。新增表單時照這個模式接上。

- **隨喜要自己一塊、而且排在加購之前**（2026-10-23 廟方：「隨喜是很重要的！」「隨喜再明顯，放在加購上面」）。原本它是「加購項目（可多選）」的最後一列，等於把它框成一件可以買的商品——隨喜不是商品是心意，擺在購物清單的尾巴，語意與份量都不對。現在是獨立的金框區塊，帶一行邀請文案與 `VOLUNTARY_PRESETS` 的常見金額快選（300／600／1200，**取自本壇自己的價目不是憑空訂的**）。
  **一定要留「自填」那一格**：隨喜的意義就是不拘金額，只給選項等於變成定價。快選鈕再按一次會清掉。
  **份量靠一條深色標頭拉開**（整個報名流程只有這一塊有）。**深底配白字，不要金底配白字**——金底 #C49820 上的白字實測只有 **3.17:1**，正是本檔記過的「金字壓在金箔上等於沒有字」；而深色的字在金底上雖有 4.92:1，卻會被 inkTheme 翻成亮色（它假設背景是深的），兩套主題顧不了。改成 `bg-temple-red` 深底＋白字：6.16:1，而且 `div` 不會被 inkTheme 的 section／button 規則碰到，深淺兩套長得一樣。
  **這一塊不要用漸層底**：對比稽核遇到 `backgroundImage` 就跳過（漸層讀不出單一顏色，那是刻意的），所以**漸層等於讓整塊對稽核隱形**——第一版就是這樣讓「NT$」在漸層亮端 3.91:1 溜過去。換成 `bg-temple-gold/15` 之後稽核跳過數從 6 降到 0，而且「金底上的 temple-red 要亮一階」那條也接得到（選擇器比對 `bg-temple-gold/`，漸層的 `from-temple-gold/` 比對不到）。
  **合計要放在所有框之外**：它原本長在加購框裡，而加購框有「沒有固定品項就整個不顯示」的條件——只設了隨喜的活動，信眾填了金額卻看不到任何合計。
  **合計放在所有項目之後**（2026-10-23 廟方：「應該要放到最後」）：方案／隨喜／加購／供品全部挑完才報總數。它也**只能有一份算式**——搬出來之前加購那塊自己也算一次。
  **供品要進合計**（2026-10-23 廟方）。這一改要動**四個地方**，少一個就是前後台金額對不起來：`ClaimedOffering` 加 `fee`（**冗餘存一份是刻意的**，活動的供品價錢日後會被改，報名當下收多少得留在那筆紀錄上）、App 送出時帶上 fee、`services/serviceAmount.ts` 的 `blessingAmount`、`api/notify-confirm.ts` 的 `blessingTotal`。
  **舊紀錄不補，這是廟方的決定**（2026-10-23：「過去就過去，之後要算」）。在那之前的 `claimed_offerings` 沒有 fee，算出來是 0——那正是當時的實際行為（供品從不進金額）。
  **看到舊紀錄算 0 不要當成 bug 去回填**：那是已經成立的財務紀錄；真要回填也不能拿現在的供品價錢去填，價錢可能已經被改過，要先查出當初實際收了多少。
  **小計要講清楚含什麼**：那個數字長在加購的框裡，而 `total = 方案費 + 加購 + 隨喜`，所以一個加購都沒勾也會顯示金額（廟方的截圖是「小計 NT$200」而上面一個都沒勾）。改成「此人合計 NT$X（含方案 NT$Y）」——在付款的畫面上，看不懂的數字比沒有數字糟。

- **後台「代為報名」（信眾資訊每一列的按鈕，2026-10-30）**：廟方直接幫信眾報名祈福活動或問事。存在的理由是「目前還是有大量的信眾從 LINE 官方帳號手動通知報名」——那些人不會自己去官網填表。

  **四個刻意的決定，廟方 2026-10-30 當場拍板，不要自行更改：**
  1. **`source` 標成 `admin/line`**（`PROXY_SOURCE`）。不標的話 `getSource()` 會回 `direct`，然後「流量來源」那一頁會說「很多人自己直接找上門」，而實際上是工作人員一筆一筆加的。**那個數字會被拿去判斷要不要繼續投廣告。** 為此 `SubmitOptions` 多了 `source?: string`，`submitBooking` 與 `createBlessingRegistration` 改成 `opts?.source ?? getSource()`。
  2. **不寄「報名成功」信**（`notify: false`）。對方剛在 LINE 跟廟方講完話，再收一封信只會困惑，而且多數 LINE 來的人沒留信箱。（2026-11-23 起改推 LINE，見下方。）**「已收款」那封不受影響**，還是廟方按下去才寄。
  3. **涵蓋祈福活動與問事，年度點燈刻意不做**（廟方：「不是年度點燈」）——點燈不是檔期性的報名。
  4. **重複報名只提醒不擋**：真的有人要報兩個名額。

  **2026-11-18 廟方改口，代為報名加上太歲點燈**（「信眾管理可以協助報名，目前有祈福活動跟問事，也加上點燈」，推翻上面第 3 條）：選燈種，專屬神明燈要再選指定神明、一樣扣名額（同前台，選項標剩幾盞、額滿停用）；生日必填；同一盞燈本季已登記算重複（只提醒）。`submitLampRegistration` 因此也收 `opts.source`，標 `admin/line`、不寄通知信。

  **2026-11-23 廟方要求代為報名要用 LINE 通知信眾**（補充上面第 2 條，email 仍然不寄）：`notify-confirm` 的 `kind: 'proxy'`，三種都有。**只推 LINE、推不出去不退 email**，結果顯示在完成畫面。只收管理員、一次一筆、`source='admin/line'` 且 10 分鐘內建立的。**不蓋任何章**（蓋 `confirm_sent_at` 會讓之後的確認通知不寄），防重複靠 LINE 的 `X-Line-Retry-Key`＝那一筆的 id。有費用才附匯款資訊；場次已過（補登）或讀不到燈種／活動設定就不推。
  **「代為報名」鈕是實心深底（`bg-temple-red` 白字＋人像圖示）**（2026-11-18 廟方：「這是重要的按鈕，請凸顯」），同一格的檢視／合併維持細框小字，不要改回跟它們一樣。
  **已截止的場次照樣列在下拉裡**（分成兩個 optgroup，已截止那組標明）。看起來很怪，但代為報名存在的理由正是「這個人錯過了前台的截止」；只給開放中的等於在最需要它的時候把它關掉。**實測 2026-10-30 當天「開放報名中」是 0 場**——四場祈福的截止日全過了——所以只列開放中的話，這個功能上線第一天打開就是空的。

  **`externalForm === 'fahui'` 的活動一律不列。** 那種的報名在 `fahui_registrations`，從這裡報下去會產生一筆對不到場次的孤兒訂單——與前台不給「我要報名」是同一個理由。

  **基本資料取名冊「最後一次留下的值」**（`latest()` 從 `records` 由新到舊找第一個非空的），不是 `phones[0]`——那是最早出現的那一支，搬過家換過號碼的人會填到舊的。拆分出來的列要用 `splitFrom` 當姓名，`name` 後面帶了生日。

  資料表 `shared_sessions`／`shared_session_entries` 與 RPC `get_shared_session` 都在資料庫裡。流程：建立共享場次 → 拿 `?share=<id>` 連結 → 親友各自填 → 一起送出；支援點燈／祈福／問事，連結 7 天到期。
  合併當天在現行 main 上重跑完整流程：`/lamps` 建立場次 → `?share=` 連結 → 填民國72年6月20日 → 生肖轉唯讀「豬年　依生日自動換算」→ 加入報名表 → RPC 讀回 `birth_date = 民國72年6月20日（農曆五月初十）`、`zodiac = 豬`，與標準合併格式一致。

  **主揪可以主動刪除**（2026-09-12 廟方要求，原本只能等 7 天到期）：面板最下方一行淡色文字「刪除這張揪團報名表」、提示卡每一列一個垃圾桶圖示。刻意做小做淡、跟「加入」「送出」拉開——長輩的手指按不準，破壞性動作不能挨著主要動作。`confirm()` 警示寫明兩件無法復原的事：名單一起刪、分享出去的連結會失效。RLS `owner_delete_shared_sessions` 只放行 `created_by = auth.uid()`；**舊場次（created_by NULL）刪不掉是刻意的**，放寬會讓任何拿到連結的人能刪別人的表，它們最多 7 天就過期。**`delete()` 被 RLS 擋下是靜默 0 列不會報錯**，要 `.select('id')` 讀回實際刪掉的列數，否則會告訴主揪「已刪除」但東西還在。
  **會員中心看得到揪團紀錄**（2026-09-12 廟方：「紀錄很重要」）：報名紀錄 tab 最上面一段「揪團報名表」，列出這個帳號開過的每一張表——進行中（繼續／刪除）、已送出（只能看，紀錄要留）、已過期沒送出（那一團沒成，主揪要知道）。資料走 `get_my_shared_history()`（`shared_sessions_history.sql`），與 `get_my_shared_sessions()` 刻意分兩支：前者回全部，後者只回還能動的給提示卡用。**為什麼不能靠既有的報名紀錄**：那是拿電話比對 `lamp_registrations` 等表撈的，揪團送出時親友填了自己電話的那幾筆掛在親友名下，主揪看不到，同一團會缺人；揪團紀錄直接列場次＋名單才是完整的一團。已送出的場次名單（`shared_session_entries`）保留不刪，就是為了這裡。
  **親友點到失效連結要有提示**：`?share=` 指到不存在的表（被刪或到期）原本靜靜 return，親友看到一般頁面會以為網站壞了。現在三個服務頁最上方顯示「找不到這張揪團報名表」並保留一般登記表讓他自行登記。
  **名單只有主揪看得到**（2026-09-12 廟方定調「要登入會員、發起揪團，才會顯示共享報名單」）：那張列出所有人的「單」是主揪的，被揪的人只看到「已有 N 人加入」的人數與自己要填的表，看不到別人的姓名、生肖、選了什麼——分享連結會被轉傳，任何拿到連結的人都不該看到別人的個資。面板標題也跟著換：主揪是「共享報名表」，被揪的人是「揪團報名」，免得以為自己在看整張單。
  **被邀請者與主揪看到的不一樣**（2026-09-10）：開了 `?share=` 但不是建立者的人，只顯示共享面板——服務介紹、方案行銷卡、以及**主揪自己的登記表**全部遮掉。最後那項是安全問題不是版面問題：那張表的「送出登記」會開一筆與揪團無關的獨立訂單，而它就長在共享面板正下方。實測改前 `/lamps?share=` 頁高 4221px、面板在 1238px、下方 3147px 起是主揪的表；改後頁高 1998px、面板在 220px。判斷式是 `isSharedGuest(type)`。
  **被揪的人要先看到活動海報**（2026-10-12 廟方要求，`SharedFormPanel` 的 `blessingEvent.imageUrl`）：
  被揪的人那一頁是刻意剝光的（上面那條 `isSharedGuest`），結果他手上只剩頂部那一行白色小字，
  不知道自己在報什麼。海報上本來就印著日期、費用、祈願文，補這一張就補齊了。
  **主揪不顯示**：他看得到完整的活動頁，同一張海報就在下面，再印一次是同一件事講兩次。
  海報可點開放大（`onPoster` → App 的 `posterUrl` 燈箱），縮圖讀不到海報上的小字。
  尺寸照全站規則**只給上限**（`w-auto h-auto max-w-full max-h-[24rem]`）——
  直式用 `w-full` 會被壓扁。實測橫式 1525×1031 → 307×208、直式 853×1280 → 256×384。
  **點燈與問事各給一張「服務海報」**（`SHARED_POSTERS`，App.tsx，廟方 2026-10-12 提供圖）：
  它們沒有「那一場」可對應——`SharedSessionConfig` 只有 blessing 存 `eventId`，
  點燈是每個人各自選燈種、問事的場次只有日期——所以用一張代表整個服務的形象圖。
  **放 `public/` 不放資料庫**（`shared-poster-lamp.jpg`／`shared-poster-booking.jpg`）：
  這是固定的服務形象圖，不像活動海報每場都換。檔名要列進 `vite.config.ts` 的 `HERO_FILES`，
  取網址用 `heroSrc()`——換圖時內容雜湊變＝網址變，信眾不會被舊快取卡住。
  祈福的順序是**活動自己的 `image_url` 優先，沒有才退回服務海報**（目前祈福沒設，行為不變）。

  **主揪必須登入會員，被揪的人不必**（2026-09-10 廟方定調，概念同 Uber Eats 揪團）：主揪有帳號才有「誰開的」可查，換裝置也找得回未送出的表；被揪的人點連結進來選方案、填資料、加入即可，不必註冊——那正是揪團要好用的關鍵。
  `shared_sessions.created_by` 記主揪的 user id。RLS：建立需 `created_by = auth.uid()`（WITH CHECK，不能只靠前端擋）、主揪 SELECT 得到自己的場次、加名單維持開放給 anon。`get_my_shared_sessions()` 回未送出且未過期的場次含名單。
  **順帶修掉一個安全問題**：`mark_shared_session_submitted` 原本 anon 也能呼叫，**任何拿到分享連結的人都能把整團送出**，主揪還沒收齊就被結單。改成只有 `created_by` 本人能送；`created_by IS NULL` 的舊場次維持原行為，否則這次改動前開的表會卡住送不出去。
  **`isCreator` 判斷要直接問 `supabase.auth.getUser()`，不要讀 `member` 狀態**：載入 `?share=` 與 `getSession()` 是兩個各自進行的非同步流程，讀 member 會賽跑——主揪自己開連結時常常還是 null，就被當成被揪的人。
  **主揪要找得回未送出的表**：共享場次是 capability 模式、沒有擁有者欄位，主揪身分只記在自己的瀏覽器，而場次 id 原本只存在網址列的 `?share=` 裡——關掉分頁就再也找不回來（廟方回報「整張訂單都不見」）。改成把清單存進 localStorage（`services/sharedSessionStore.ts`），三個服務頁的**最上方**顯示提示卡。放在表單上方量到是 1238px，手機得先滑過四張行銷卡，等於沒提醒；移到區塊頂端後是 160px。換手機仍然找不回來，這是不要求登入的必然代價。
  **旗標的值就是正式站的值**：main 上 `ENABLE_GROUP_BOOKING` 是什麼，廟方按後台「重新發布」觸發 Deploy Hook 從 git 重建後就是什麼。要再停用或改動，未驗過的先留在分支（本檔部署紀律第 0 條記載的事故）。
  **教訓：停用中的功能不會出現在任何掃描結果裡，全站統一規則時要主動把旗標關閉的區塊列進清單。**2026-08-11 全站統一生肖規則時，揪團就是因為停用而被漏掉（原本還是「自動帶入可手動修改」的下拉，那正是造成生日與生肖矛盾的寫法），拖到 9/02 才補。
- **送出前檢查「本人」**（2026-11-27 廟方：會員鍾介凡幫鍾木森點燈卻顯示「鍾木森 #本人」）：第一張卡預設本人並帶入會員資料，會員把姓名改成家人的卻沒改稱謂。四個表單送出前 `confirmSelfLabels`：不只一位本人→擋；本人那張姓名≠會員姓名→確認視窗（不直接擋，會員資料可能是舊名）。訪客只檢查第一條。舊資料用 `supabase/queries/self_label_suspects.sql`（只讀）找。後台代為報名固定標本人是對的（替那個人自己報）。
- **填寫當下的防呆**（同日廟方「有辦法預防嗎？防呆」）：本人那張改了姓名、離開姓名欄就清空稱謂（`releaseSelfLabel`，會員才比得了姓名）；「本人」只能一位，別張選了就變灰「本人（已有一位）」；稱謂必填，沒選時選單紅框。捐獻原本沒有稱謂欄，2026-11-27 補上。送出前的 confirmSelfLabels 仍是最後一道。

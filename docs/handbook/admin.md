  **側邊欄的紅點來自 `badgeFor()`，而它只看得到 `fetchAll` 抓進來的資料**（2026-11-17 廟方：「緊急祈願⋯⋯後台的清單沒有顯示小紅點」）。緊急祈願的資料原本只在 `AdminUrgentTab` 裡自己抓，總覽層拿不到，紅點永遠是 0、不會報錯。現在 `fetchAll` 一起抓一次算 `urgentPending`，進到那一頁後由 `onPendingChange` 回報即時數字。**自己抓資料的分頁要有紅點，就得照這個模式接回來**，光在 `badgeFor` 加一行是沒有用的。
  **紅點一律是「還要廟方動手的筆數」**（同日廟方：「小紅點很重要，因為有小紅點才會去檢查操作回覆」）：問事待處理、點燈／祈福／**捐獻**待匯款、法會 pending、志工待聯絡、緊急祈願待處理。捐獻原本是「24 小時內的新捐款」，放一天就自己消失，線上當時有 5 筆待匯款卻是 0，已改。**捐獻的狀態資料庫裡有英文 `pending` 與中文 `待匯款` 兩種**（`pending` 是那一欄原本的預設值，`submitDonation` 又沒明寫 status），讀取端由 `normalizeDonationStatus` 折成中文，寫入端現在明寫 `待匯款`。查線上資料時點燈 3 筆都已收款，所以點燈沒紅點是對的，不是壞掉。
  **後台「總覽」2026-11-18 依廟方決定重做**（廟方：「最早當初我們是為了法會報名，但現在已升級成整個和聖壇的管理，需求不同，dashboard 重點也就不同」）。第一版把四張累計數字卡、LINE 導流、最新報名都拿掉、只剩三塊；**同一天廟方看過之後又改**：「頂端四張累計數字卡、LINE 導流和最新報名，改回來，但四張數字的內容，我要改成符合現在有意義的。」「近期行程太長了，改一週內」（2026-11-18）。現在由上而下（`OverviewTab`）：**四張數字卡 → 今天要做的事 → 近期行程 → 本月款項 → 最新報名 → LINE 導流**。
  (0) **四張數字卡**（`overviewStats`，手機 2×2、`lg` 一排四張；所有看得到總覽的角色都看得到；那一頁這個角色進得去才可點）。舊的四張（總報名數／待處理／累計捐款／不重複信眾）都是開站以來的累計，只會變大、看不出現況，待處理又與「今天要做的事」重複，所以換成：
  - **遷址累積金額**：`type = '遷址護持'` 的捐獻，**已收款**才進主數字；另列待匯款與「未核對」——status 為空的是收款狀態上線前的舊資料，**從未核對過、不等於沒收到**（同 `buildIncomeRows` 的 unchecked），兩邊都不能硬塞。已取消不算。人數依電話去重，沒留電話的一筆算一人。點了到捐獻管理。遷址是現在全壇最重要的募款，這張卡回答「募到多少了」。
  - **本月報名筆數**（上月對照）：問事／點燈／祈福／法會／捐獻，依報名時間的**本地月份**歸月、不含已取消；法會一張報名單算 1 筆（不是牌位數）。**志工不算**——那不是報名一項服務。
  - **本月新信眾**（上月對照）：依電話（只拿掉空白與連字號），**第一次出現**在問事／點燈／祈福／捐獻／法會／志工任何一張表的月份是本月的人數。空電話不參與（同 `samePhone` 的理由）。已取消的也算「來過」。點了到信眾資訊。
  - **會員人數**：**一個人有好幾個帳號只算一次**，走 `toPersonKey()`（2026-11-18 從 `MembersTab` 搬到模組層級共用，`samePhone()` 也一起搬），與會員資訊的標題數字一致；「本月新增」取那個人**最早**帳號的建立月份（同會員資訊的「加入」）。點了到會員資訊。
  (1) **今天要做的事**：一格一個還要動手的事（問事待處理、點燈待匯款⋯⋯），點了跳那一頁。**格子直接用父層的 `badgeFor`＋`navItems` 組（`overviewTodos`），不在總覽另抄狀態規則**——舊版重抄了四條，紅點改規則就對不上。新增有紅點的分頁時記得在 `TODO_LABEL` 補一句動作，沒補會退回「分頁名＋待處理」。提醒信眾也住在這裡（見上面「寄送提醒」那條），讀不到名單時不出格子、只留一行小字。
  (2) **近期行程**（未來 **7 天**，`AGENDA_DAYS`；原本 14 天，廟方嫌太長，本地日期）：問事場次（`getBookingSessions(false)`＋`getBookingCountsBySession`，同問事管理）、祈福活動（開始日或報名截止落在窗內；`external_form = 'fahui'` 的數字取法會報名筆數）、神明聖誕（`resolveFeastDate`，含小月改列廿九）。依日分組，日期旁一定帶農曆。自己抓的資料失敗一律當空的。
  (3) **本月款項**：**只給看得到應收管理的角色（admin／finance），staff 不顯示**。金額走 `buildIncomeRows()`——2026-11-18 從 `ReceivablesTab` 抽出、兩頁共用，不要再各算一份。依報名日期歸月、不含已取消，是**報名金額不是已入帳**，畫面上有寫。
  (4) **最新報名**與 (5) **LINE 導流**：照第一版之前的樣子搬回來（`lineStats` 由父層 `fetchAll` 的 `getLineClickStats()` 抓）。最新報名四個分頁的紅點**改用父層 `badgeFor` 算好傳進來**（`serviceBadges`），不再在總覽自己抄狀態規則；日期改成本地那一天（原本是 `createdAt.slice(0,10)`，UTC）。
  **新增後台分頁要動五個地方**：`type Tab`、`allNavItems`、`NAV_GROUPS`、`types.ts` 的 `ROLE_ALLOWED_TABS`、以及渲染區塊的 `{tab === '…' && <XxxTab />}`。漏掉 `ROLE_ALLOWED_TABS` 會被 `navItems` 濾掉、選單上完全看不到，而且沒有任何錯誤訊息。
  **選單的順序以 `NAV_GROUPS` 的 `keys` 為準**（2026-10-13 改）：在那之前組內順序其實跟著 `allNavItems` 走，**調整 keys 的先後畫面完全不會變**，而程式碼看起來明明改對了。一份清單只能有一個順序來源，放在 keys 才是人會去改的地方；`allNavItems` 現在只負責「有哪些分頁、叫什麼、什麼圖示」。
  改這個順序時**只動被要求的那一組**：後台是廟方每天在用的，順手「順便整理」其他組等於破壞他們的肌肉記憶。2026-10-13 把順序來源換成 keys 時，另外兩組的順序跟著變了（roster/members、shower 各差一位），已把那兩組的 keys 設回原本畫面上的順序。
  **「常用」組內也有先後**：每天會用的排前面，檔期性的排後面。法會報名（只剩財務組有）跟著一場法會跑，排在最後。志工報名 2026-11-25 併進信眾資訊、不在選單上。

  **`confirm()` 要在 `setForm` 外面叫**：寫進 updater 裡 StrictMode 會把它跑兩次，視窗就跳兩次。

- **後台分頁的 UI 要怎麼驗（它需要登入，開發時進不去）**：用 Vite 的模組圖把單一 tab 元件掛到一個浮層上測。

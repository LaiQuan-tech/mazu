- **遷址方案手機卡片**（`components/RelocationPage.tsx`）：只列「這一級有的」項目，沒有的不要畫灰色「—」。桌機是矩陣表格、橫向能比較各級差異，畫「—」才有意義；手機一級一張卡沒有比較對象，列一堆「—」是干擾（廟方明確反映過）。金額的「元」由 `withCurrency()` 在渲染層補，後台只存數字，「隨喜」這種非數字不會被加上單位。

- **遷址有自己的登記表**（`RelocationDonationForm`，`components/RelocationPage.tsx`，2026-10-23 廟方：「遷址捐款，最後面的捐款也要填寫姓名、性別、出生年月日、地址，還有要哪個捐款方案」）。
  在那之前那一頁只有一組帳號：信眾匯了款，廟方只看到一筆入帳，不知道是誰、選的是哪一級——而方案裡寫著「誦經祈福」與「遷址功德簿」，兩樣都要姓名生辰地址才做得出來。
  **寫進既有的 `donations`、`type = '遷址護持'`**（同「神尊修復」那一套）。不另開一張表：後台的捐獻管理、應收、流量來源、信眾名冊與感謝信全都已經讀 `donations`，另開一張等於那五個地方各漏一塊。
  **`遷址護持` 與 `神尊修復` 永遠排除在一般捐獻的下拉之外**（`EXCLUDED_TYPES`，App.tsx），**資料庫那份清單也要濾一次**——廟方哪天在後台把它建成一個類別，它就會出現在一般捐獻頁上，而那一項收的是**另一個銀行帳戶**。
  **護持方案選在最前面**（廟方 2026-10-24）。先決定「要哪一個方案」再填「我是誰」才是信眾腦中的順序；而且金額是跟著方案走的，填完一整頁姓名生辰才發現這一級不是自己要的，等於白填。同問事表單把場次移到人員卡片之前那一次（2026-10-12）。
  **金額欄與小計要跟著方案一起搬**：金額只有「隨喜」「10 萬以上」那兩種級距才出現，小計也只由方案與級距算出來——它們與方案是同一件事，拆開就變成「在上面選方案、在下面某處才看得到自己選了多少錢」。
  **這不牴觸祈福報名表那條「合計放到最後」**：那一頁的合計由方案、隨喜、加購、供品四樣加總，所以得等全部選完；這裡的金額只由方案決定，底下的欄位一個都不會改變它。
  **金額跟著方案走，不讓人自己打**：方案表上就是那幾級，自由輸入只會出現對不上任何一級的金額，廟方得回頭一個一個問。只有「隨喜」與「100,000 以上」這種本來就沒有固定數字的級距才開一格讓他填（`isOpenTier`／`tierFloor`）。
  **級距單獨存一欄**（`relocation_tier`）不是併進方案名：廟方要統計得出各級各幾人。方案與級距都**存文字不存 id**，同 `donations.type` 的理由——方案表在後台改得動，歷史紀錄要維持當初登記的樣子。
  **成功畫面不要再印一次匯款帳號**：它緊接在 `RemittanceNotice` 之上，兩塊各印一次帳號與「請填後五碼」就是同一件事講兩遍（第一版這樣寫，截圖一看就知道不對）。成功畫面要講的是「錢還沒付、金額多少、往下看」。
  **會員資料自動帶入走 prop 不走 import**：這一頁是懶載入的，從 App.tsx 反向 import 就是循環相依（同 BulletinBody／BankInfoBox 那條）。App 往下傳 `donorDefaults`，規則同四個表單——**只補空欄位**，而且帶入生日要換 `key` 強迫 `BirthDatePicker` 重新掛載。

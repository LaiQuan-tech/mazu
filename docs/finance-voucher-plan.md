## 二、三個必須先改的認知

### 1. 那是紙本版面，不是資料模型

金額拆成「佰萬／拾萬／萬／仟／佰／拾／元」七格，是**紙本防竄改**的作法——每格一個數字，事後加不上去。

做成網頁時**不要做七個輸入框**。理由不只是難用：七個欄位就是七個可以各自寫錯的地方，而且「12,345」要拆進哪幾格由程式決定，一旦有人只改其中一格，資料就自相矛盾且無法偵測。

**正解是分開兩件事**：
- **資料**：`amount integer`，一個數字。
- **列印**：要印成傳票時，由那個數字**當場排進格子**。版面完全一樣，但資料只有一份。

### 2. 合計金額要用算的，不能用填的

紙本上合計是人加的。系統裡如果單頭的合計和明細加總對不起來，**沒有任何方法知道哪個才對**。所以合計不存進資料庫，一律由明細即時加總。

這跟本專案既有的原則一致：捐款類別存文字不存 id、生肖由生日推算不開放手選——**能算出來的就不要讓人填**。

### 3. 四個簽章，但後台只有兩個帳號

表單有總幹事、執行長、會計、財務四關，而目前 `admin_profiles` 只有兩個帳號、三種角色（admin／staff／finance）。四關簽核沒有人可以簽。

這是**必須廟方決定**的事，見第五節。

## 三、最重要的一件事：收入不要再建第四套

支出是全新的——全專案搜「支出／憑證／發票／收據／報帳」**零命中**，沒有平行系統的風險。

但**收入已經有三套不一致的作法**：

| 現況 | 位置 | 問題 |
|---|---|---|
| 應收管理 | `AdminDashboard.tsx:5389` | **純唯讀報表**，零寫入、零匯出。名字叫「應收」，但它不知道錢有沒有真的進來——狀態直接沿用報名單自己的狀態，捐獻更是硬寫「已完成」 |
| 法會對帳 | `fahui_registrations` 的 7 個欄位 | 唯一真的在對帳的地方（付款方式／付款日期／後五碼／財務確認／會計確認／感謝狀編號／備註），但**欄位掛在法會報名表上**，所以點燈、祈福、捐獻完全享受不到 |
| 捐獻 | `donations` | **連「錢收到了沒」都沒有欄位**，UI 硬寫「已完成」 |

**如果再做一張獨立的「收入憑證」表讓人手動輸入金額，那就是第四套，而且是最糟的一套**——同一筆錢會同時存在報名紀錄與憑證裡，兩邊金額可以不一樣，誰也不知道該信哪個。

**正確的分工是**：

> **報名紀錄 = 業務事實**（誰、報了什麼、應付多少）
> **憑證 = 財務事實**（這筆錢什麼時候、用什麼方式、由誰經手進出）

所以收入憑證**引用**來源紀錄（`source_table` + `source_id`），金額從來源帶入、不重新輸入。而法會那 7 個對帳欄位，長期應該被憑證吸收——那樣四種服務都有對帳，而不是只有法會。

## 四、資料表設計

```sql
-- 會計科目（照 donation_types 的模式：後台可增刪改，不要自由文字）
accounting_accounts (
  id, code, name,
  direction  'expense' | 'income' | 'both',
  sort_order, is_active
)

-- 憑證單頭
vouchers (
  id uuid,
  direction     'expense' | 'income',
  voucher_no    text UNIQUE,          -- 單號
  voucher_date  date,                 -- 傳票日期
  summary       text,
  status        'draft' | 'submitted' | 'approved' | 'void',
  note          text,
  created_at, created_by
  -- 刻意不存 total：由明細加總
)

-- 明細（一單多筆）
voucher_items (
  id, voucher_id, seq,
  account_id    → accounting_accounts,
  summary       text,
  amount        integer,              -- 元，整數。不拆格子
  applicant     text,                 -- 申請人
  -- 收入憑證才用：引用來源，不重新輸入金額
  source_table  text NULL,            -- donations / lamp_registrations / ...
  source_id     uuid NULL
)

-- 附件（發票、收據、傳票影本）
voucher_attachments (
  id, voucher_id, item_id NULL,
  kind          '支出傳票' | '發票' | '收據' | '其他',
  storage_path  text,                 -- 私有 bucket
  file_name, mime, size,
  uploaded_at, uploaded_by
)

-- 簽核
voucher_signatures (
  voucher_id, role '總幹事'|'執行長'|'會計'|'財務',
  signer_name text,                   -- 誰簽的
  signed_at   timestamptz,
  signed_by   uuid NULL               -- 有系統帳號才填
)
```

**`status` 為什麼需要**：傳票打到一半不該被當成正式單。`void`（作廢）而不是刪除——財務資料不刪，這與捐款類別「有紀錄就禁止刪除」的既有原則一致。

## 五、附件必須放「私有」bucket

目前全站只有 `site-images` 一個 bucket，而且所有上傳都走 `getPublicUrl`——**是公開的**，路徑還是 `bulletins/<timestamp>.jpg` 這種可猜的格式。

發票與收據上有金額、統一編號、可能有個資。**不能放那裡。** 要新建一個私有 bucket，讀取一律走 `createSignedUrl`（短效簽名網址），RLS 只放行管理員與財務組。

這是整個功能裡**唯一會外洩敏感資料的地方**，不能沿用既有作法。

## 七、建議的順序

**第一階段：支出憑證（全新、自成一格、不碰任何既有資料）**
科目表 → 憑證 CRUD → 附件（私有 bucket）→ 列印版面（金額當場排進格子）。
這一階段完全不影響現有功能，可以先上線給財務用。

**第二階段：收入憑證（接既有資料）**
從報名／捐獻紀錄「開立憑證」，金額帶入不重填。同時把法會那 7 個對帳欄位的語意搬進憑證，讓點燈／祈福／捐獻也有對帳。

**第三階段：報表**
依會計科目、依期間的收支表。這一階段才有資格取代「應收管理」那頁——在那之前它至少還是個收入彙總。
